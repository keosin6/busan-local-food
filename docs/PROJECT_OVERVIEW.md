# 프로젝트 개요

## 1. 프로젝트 이름

**busan-local-food** — 부산 맛집 정보 및 리뷰 공유 플랫폼

## 2. 목표

- 부산 지역의 맛집을 한곳에서 찾을 수 있게 합니다.
- 사용자가 직접 맛집을 등록하고, 리뷰와 평점을 남겨 정보를 함께 쌓아갑니다.
- 리뷰가 충분히 쌓인 맛집은 AI가 리뷰를 요약해 빠르게 특징을 파악하게 합니다.
- 플랫폼에 등록된 맛집 안에서 AI가 취향에 맞는 곳을 추천합니다.

## 3. 대상 사용자

| 사용자 | 설명 |
|--------|------|
| 비회원 (Guest) | 맛집 목록, 상세, 검색, 리뷰 열람, AI 요약 열람 |
| 일반 회원 (USER) | 위 기능 + 맛집 등록, 본인 맛집 수정·삭제, 본인 리뷰 작성·삭제, 찜, AI 추천 |
| 관리자 (ADMIN) | 일반 회원 기능 + 전체 맛집·리뷰 관리, 회원 조회, 관리자 대시보드, S3 삭제 재시도 (F1-09) |

> 권한 구분은 회원의 `role`(`USER`, `ADMIN`)로 합니다. 맛집 수정·삭제 권한 정책은 [FUNCTION_SPEC.md](FUNCTION_SPEC.md)의 F1-02 절, 관리자 권한은 F1-09 절을 따릅니다.

## 4. 범위

### 포함 (필수 기능)

| ID | 기능 |
|----|------|
| F1-01 | 회원가입, 이메일 로그인, 로그아웃, 화면 세션 인증과 API JWT 인증(Access/Refresh Token), Google 로그인, 기존 계정에 Google 계정 직접 연동·해제 |
| F1-02 | 맛집 등록, 수정, 삭제(관련 데이터와 S3 이미지 포함 완전 삭제), 목록, 카테고리, 검색 |
| F1-03 | 맛집 이미지 AWS S3 업로드 |
| F1-04 | 리뷰 작성 및 삭제, 평점, 평균 평점 |
| F1-05 | 리뷰 3개 이상일 때 AI 리뷰 요약 및 DB 캐싱 |
| F1-06 | 찜하기 및 찜 목록 |
| F1-07 | DB에 등록된 맛집만 대상으로 한 AI 맛집 추천 |
| F1-08 | 메인 페이지, 카테고리 및 최신 맛집 |
| F1-09 | 관리자 기능: 전체 맛집·리뷰 관리, 회원 목록 조회, 관리자 대시보드, S3 삭제 재시도 (Q5에 따라 필수 범위에 포함) |

### 선택 기능

- 현재 선택 기능으로 분류된 항목은 없습니다. 기존에 선택 기능으로 분류되어 있던 관리자 기능은 Q5 결정에 따라 F1-09 필수 기능으로 편입했습니다.

### 제외 (현재 범위 밖)

- 모바일 앱 (네이티브 앱)
- 예약, 결제, 주문 기능
- 외부 지도 API 기반 맛집 자동 수집 (맛집은 사용자가 등록)
- 관리자 승인 워크플로우 (맛집 등록 전 승인 절차는 포함하지 않음. 필요 시 설계 변경 절차로 검토)
- 회원 정지·탈퇴 기능의 세부 정책 (T1, 확정 전까지 범위 미정)

> 제외 항목을 범위에 넣으려면 [DEVELOPMENT_RULES.md](DEVELOPMENT_RULES.md)의 설계 변경 절차를 따릅니다.

## 5. 기술 스택 (고정)

| 영역 | 기술 |

| 언어 | Java 21 |

## 6. 아키텍처 개요

```
[브라우저]
    │  HTTP (HTML: Thymeleaf / JSON: REST)
    ▼
[Spring Boot 애플리케이션 on AWS EC2]
    ├─ Spring Security  : 회원 인증 (화면 세션, API JWT, Google OAuth2)
    ├─ Controller       : 화면 렌더링 + REST API
    ├─ Service          : 비즈니스 로직 (맛집, 리뷰, 찜, AI 요약·추천)
    ├─ Repository (JPA) : 데이터 접근
    ├─ Spring AI ───────────► [OpenRouter] ─► LLM
    └─ S3 Client ───────────► [AWS S3] (맛집 이미지)
    │
    ▼
[MySQL 8]  ← 같은 EC2 내부에 설치, 외부 3306 비공개
```

- 모놀리식 구조입니다. 화면과 API는 하나의 Spring Boot 애플리케이션에서 제공합니다.
- 이미지 바이너리는 DB에 저장하지 않고 S3에 저장합니다. DB에는 S3 객체 키만 저장합니다.
- DB와 S3는 분산 트랜잭션으로 묶지 않습니다. S3 삭제 실패는 `storage_delete_task`로 추적하고 관리자가 재시도합니다 (NFR-17).
- AI 호출은 서버에서만 수행합니다. 브라우저에 API 키를 노출하지 않습니다.
- 관리자 화면(`/admin/**`)과 관리자 API(`/api/admin/**`)는 일반 회원 영역과 분리하고, 권한은 서버에서 검증합니다.
- 인증 구분: 화면은 HTTP 세션, API(`/api/**`)는 JWT입니다. Google 일반 로그인은 화면 세션과 JWT를 함께 발급합니다. Google 계정 연동은 로그인된 회원의 HTTP 세션에서 시작하며, 연동 중 기존 세션과 JWT를 유지합니다. 연동 대상 회원은 연동 시작 시점의 세션에서 확보합니다 (T11 A안 확정). Google 신규 가입은 닉네임 설정 후에만 회원을 만듭니다 (T3 A안). Refresh Token 재사용이 탐지되면 회원의 모든 활성 토큰을 폐기합니다 (T7 A안). 연동 해제는 현재 비밀번호 재입력으로 본인을 확인합니다 (T8 A안). 화면 로그아웃은 API 로그아웃을 먼저 수행합니다 (T12 A안). API 401은 재발급 1회 후 원요청을 1회 재시도합니다 (T13 A안). 구현은 Stage 2입니다.

## 7. 배포 개요

- GitHub Actions: `main` 병합 또는 태그 기준으로 빌드·테스트 후 EC2에 배포 (세부 절차는 구현 단계에서 확정)
- EC2(Ubuntu): Spring Boot JAR 실행, 환경 변수는 서버에만 보관 (`prod` 프로필)
- MySQL 8: 같은 EC2 내부에 설치합니다 (Q4). 데이터는 재시작·재생성에도 유지되는 영속 저장소에 둡니다 (NFR-13). 설치 방식과 저장소 구성은 T5에서 확정합니다.
- 3306 포트는 외부에 공개하지 않습니다 (NFR-14).
- 정기 백업을 수행합니다. 주기와 저장 위치는 T4에서 확정합니다 (NFR-15).
- 추후 트래픽이나 운영 요구가 늘면 RDS로 옮길 수 있도록 DB 접속 정보는 환경 변수로만 다룹니다 (NFR-16).

## 8. 성공 기준

- 9개 필수 기능(F1-01 ~ F1-09) 모두 동작하고 기능별 테스트가 통과합니다.
- ERD, API 명세, 실제 구현이 서로 일치합니다.
- 리뷰 3개 이상인 맛집의 AI 요약이 한 번 생성된 뒤 DB에서 재사용됩니다.
- AI 추천 결과에 DB에 없는 맛집이 포함되지 않습니다.
- 맛집 삭제 후 DB 행과 S3 객체가 모두 정리되거나, 실패한 S3 키가 재시도 대기 목록에 남습니다.
- 일반 회원이 `/api/admin/**`에 접근하면 403이 반환됩니다.
