# 요구사항 명세

이 문서는 기능·비기능 요구사항의 기준입니다. 기능별 상세 흐름과 예외 처리는 [FUNCTION_SPEC.md](FUNCTION_SPEC.md), 데이터 구조는 [DATABASE_ERD.md](DATABASE_ERD.md), 엔드포인트는 [API_SPEC.md](API_SPEC.md)를 봅니다.

우선순위: **M** = 필수(Must), 이 문서의 모든 M 항목은 반드시 구현합니다.

## 1. 기능 요구사항

### F1-01 회원 (인증)

| ID | 요구사항 | 우선순위 |
|----|----------|----------|
| FR-01-01 | 이메일, 비밀번호, 닉네임으로 회원가입할 수 있다. 닉네임은 중복될 수 없다 (`uk_member_nickname`, FR-01-23). 입력 규칙은 FUNCTION_SPEC F1-01 "회원가입·로그인 검증 규칙"을 따른다. | M |
| FR-01-02 | 비밀번호는 단방향 해시(BCrypt)로 저장한다. | M |
| FR-01-03 | 이메일과 비밀번호로 로그인할 수 있다. 화면 로그인은 Spring Security 세션과 JWT를 함께 발급하고, API 로그인은 JWT만 발급한다. | M |
| FR-01-04 | Access Token(JWT)과 Refresh Token을 분리하여 발급한다. | M |
| FR-01-05 | Refresh Token 원문은 브라우저의 HttpOnly Cookie에만 저장하고, DB에는 SHA-256 해시값만 저장한다. | M |
| FR-01-06 | Refresh Token으로 Access Token을 재발급할 수 있다. 재발급 시 기존 Refresh Token을 폐기하고 새 Refresh Token으로 교체한다(로테이션). 폐기된 Refresh Token의 재사용 처리는 FR-01-24를 따른다. | M |
| FR-01-07 | API 로그아웃은 해당 Refresh Token을 폐기하고 JWT 쿠키를 제거한다. 화면 로그아웃은 세션을 무효화하고 JWT 쿠키를 제거하며, API 로그아웃이 성공한 뒤에만 실행한다 (FR-01-25). | M |
| FR-01-08 | 인증이 필요한 API는 유효한 JWT 없이, 인증이 필요한 화면은 유효한 Spring Security 세션 없이 접근할 수 없다. 두 인증 수단은 서로 대체할 수 없다. | M |
| FR-01-09 | Google OAuth2 계정으로 로그인할 수 있다. Google 계정의 이메일과 같은 이메일의 기존 이메일 계정이 있어도 **자동으로 연결하지 않는다.** | M |
| FR-01-10 | 기존 이메일 계정 사용자는 먼저 기존 계정으로 로그인한 뒤, 마이페이지에서 Google 계정을 **직접 연동**할 수 있다. | M |
| FR-01-11 | 한 Google 계정은 하나의 회원 계정에만 연결할 수 있다. 이미 다른 회원에게 연결된 Google 계정은 중복 연결할 수 없다. | M |
| FR-01-12 | Google 계정 연동과 해제는 로그인된 본인 세션에서만 수행한다. 연동 시작은 CSRF 토큰을 포함한 화면 POST로 처리하고, 해제는 현재 비밀번호를 다시 입력해야 한다 (T8 A안, DEVELOPMENT_RULES 5.7.5). | M |
| FR-01-13 | 회원에게 남은 로그인 수단이 없게 되는 Google 연동 해제 요청은 거부한다. | M |
| FR-01-14 | Google OAuth2 인증 진행 중의 `state`와 연동 요청 회원 정보는 서버 임시 세션에만 보관하고, 인증 흐름이 끝나면 제거한다. 임시 세션은 회원의 로그인 상태를 나타내지 않는다. | M |
| FR-01-15 | Google 계정 연동은 로그인된 회원의 HTTP 세션에서 시작하고, 세션의 회원 ID를 연동 대상으로 저장한다. 연동 시작 요청은 CSRF 토큰을 포함한 화면 POST로 처리한다. 콜백은 OAuth2 `state`를 검증한 뒤 세션의 연동 진행 상태와 연동 대상 회원 ID를 기준으로 처리하며, Access Token의 유효기간에 의존하지 않는다. Google 이메일로 회원을 판단하지 않는다. 기존 UNIQUE 제약으로 다른 회원과의 중복 연결을 막는다. | M |
| FR-01-16 | 일반 API 인증은 JWT 기반을 유지한다. OAuth2 임시 세션은 Google 인증 과정에만 사용하며 API 인증을 대체하지 않는다. 인증 완료 후에는 JWT 체계로 돌아간다. | M |
| FR-01-17 | 화면 로그인, 화면 회원가입 후 자동 로그인, Google 로그인이 성공하면 Spring Security 세션과 JWT(Access Token, Refresh Token)를 함께 발급한다. | M |
| FR-01-18 | API 로그인과 API 회원가입은 JWT만 발급하며 Spring Security 세션을 만들지 않는다. 화면 세션은 API 인증을 대체하지 않는다. | M |
| FR-01-19 | API 인증 경로(`/api/**`)와 화면 인증 경로를 Spring Security 필터 체인으로 분리한다. OAuth2 경로(`/oauth2/**`, `/login/oauth2/**`)는 화면 체인에서 처리하며 API 체인에 포함하지 않는다. | M |
| FR-01-20 | CSRF 보호는 화면 세션 쿠키 기반 요청과 JWT 쿠키 기반 API 상태 변경 요청 모두에 적용한다. Bearer 헤더 요청은 CSRF 헤더를 요구하지 않는다. | M |
| FR-01-21 | Google 일반 로그인과 Google 계정 연동은 처리 경로를 분리한다. 계정 연동 처리는 기존 로그인 세션과 API JWT를 교체하거나 재발급하지 않는다. 계정 연동 콜백에서 일반 로그인 성공 처리를 실행하지 않는다. | M |
| FR-01-22 | Google 전용 회원(비밀번호 없음)은 로그인된 본인 세션에서 로컬 비밀번호를 설정할 수 있다. 비밀번호를 설정하기 전에는 Google 계정 연동을 해제할 수 없다. 비밀번호는 BCrypt로 해시하여 저장한다 (DEVELOPMENT_RULES 5.7.5). | M |
| FR-01-23 | Google 신규 가입은 닉네임 설정 단계를 거친다. Google 프로필 이름을 닉네임으로 자동 사용하지 않는다. 닉네임은 2~20자이며 중복될 수 없다. 닉네임 검증이 끝나기 전에는 회원을 만들지 않으며, 설정이 끝나기 전에는 정식 로그인 회원으로 취급하지 않는다. 닉네임 중복은 사전 검사와 DB UNIQUE 제약(`uk_member_nickname`)으로 막는다 (T3 A안, DEVELOPMENT_RULES 5.7.3). | M |
| FR-01-24 | 폐기된 Refresh Token이 다시 사용되면 재사용으로 판단하고, 해당 회원의 모든 활성 Refresh Token을 같은 트랜잭션에서 폐기한다. 회원은 다시 로그인해야 한다. 폐기된 토큰의 해시 행은 삭제하지 않는다. 재발급과 재사용 탐지는 회원 행 잠금 안에서 재조회 후 판정하며, 재사용 탐지 결과는 커밋 후 응답한다 (T7 A안·T14 A안, DEVELOPMENT_RULES 5.7.4). | M |
| FR-01-25 | 화면 로그아웃은 `POST /api/auth/logout`을 먼저 호출하여 Refresh Token을 폐기한 뒤, 성공한 경우에만 `POST /logout`으로 화면 세션을 무효화한다. 첫 요청이 실패하면 화면 세션을 종료하지 않고 재시도를 안내한다. `refresh_token` 쿠키의 Path는 `/api/auth`를 유지한다 (T12 A안, DEVELOPMENT_RULES 5.7.2). | M |
| FR-01-26 | 화면에서 API 요청이 Access Token 만료로 401을 받으면 `POST /api/auth/refresh`를 한 번 호출하고 원래 요청을 최대 한 번 재시도한다. 동시에 여러 요청이 401을 받아도 재발급은 한 번만 실행한다. 재발급 실패 시 재로그인을 안내하며, 재발급 API가 다시 401을 반환하면 재호출하지 않는다. 화면 세션은 이 과정에서 갱신하지 않는다 (T13 A안, DEVELOPMENT_RULES 5.7.2). | M |
| FR-01-27 | 같은 브라우저의 여러 탭이 동시에 401을 받으면 Web Locks API로 갱신을 직렬화하고, 잠금 안에서 인증 상태를 다시 확인하여 이미 갱신되었으면 Refresh 요청을 보내지 않는다. Web Locks API는 보안 컨텍스트(운영 HTTPS, 로컬 `localhost`)에서만 사용한다. 보안 컨텍스트가 아니거나 미지원인 환경에서는 같은 탭의 single-flight만 보장하며, 여러 탭의 동시 갱신은 완전히 방지하지 못한다 (T14 A안, DEVELOPMENT_RULES 5.7.2). | M |
| FR-01-28 | 로그인은 정규화 이메일+IP 조합 기준 최근 15분 실패 5회를 넘으면 6번째 요청부터 `429`를 반환하고, IP 기준 최근 15분 실패 20회를 넘으면 21번째 요청부터 `429`를 반환한다. 비밀번호는 제한된 요청에서 검증하지 않는다. 로그인 성공 시 해당 이메일+IP의 실패 기록을 초기화한다 (R1, API_SPEC 1.4). | M |
| FR-01-29 | 회원가입(화면, API, Google 신규 가입 닉네임 제출)은 IP별 최근 1시간 5회를 넘으면 6번째 요청부터 `429`를 반환한다. 입력값 검증 실패도 요청으로 계산한다 (R1). | M |
| FR-01-30 | Refresh 요청은 Refresh Token 계열별 최근 1분 10회를 넘으면 11번째 요청부터 `429`를 반환한다. 폐기된 토큰 재사용의 전체 폐기(FR-01-24)는 이 제한 때문에 생략되지 않는다 (R1, R4). | M |
| FR-01-31 | Google OAuth2 시작·콜백 및 계정 연동 콜백은 IP별 최근 15분 10회를 넘으면 11번째 요청부터 `429`를 반환한다. 시작과 콜백은 같은 IP 카운터를 공유한다. 제한 시 OAuth2 임시 상태만 정리하고 기존 화면 세션과 API JWT는 유지한다 (R1). | M |
| FR-01-32 | 제한 응답은 HTTP `429`, 오류 코드 `RATE_LIMITED`, `Retry-After` 헤더를 사용한다. 제한 기준과 내부 키 정보는 노출하지 않는다. 429 응답은 JWT 쿠키를 바꾸지 않는다. 제한된 요청은 새 이벤트를 만들지 않는다. 모든 기준은 Rolling Window로 계산한다 (R1). | M |
| FR-01-33 | 로그인 제한 이벤트에는 정규화 이메일과 IP의 HMAC-SHA256 값만 저장하고 원문 이메일과 원문 IP를 저장하지 않는다. HMAC 비밀키는 EC2 환경 변수로 주입하고 Git에 커밋하지 않는다. 프록시 뒤에서는 신뢰하도록 설정된 프록시가 전달한 IP만 사용한다. 회원가입과 Google 제한, 로그인 IP 보조 제한의 IP 키 저장 형식은 T16 결정 전까지 확정하지 않는다 (R2). | M |
| FR-01-34 | 로그인, 회원가입, Refresh 이벤트는 24시간 보관 후 삭제한다. 조회 범위를 벗어났다는 이유만으로 즉시 삭제하지 않는다. 요청 시 정리와 주기적 정리를 병행한다 (R3). | M |
| FR-01-35 | 요청 제한 판단은 MySQL 행 잠금으로 같은 키의 요청을 직렬화한다. 단순 `COUNT` 후 `INSERT`로 구현하지 않는다. 여러 키를 잠글 때는 키의 사전순으로 잠근다 (R3, DATABASE_ERD 2.10 설계안). | M |
| FR-01-36 | Refresh Token 행은 서버가 만든 UUID `family_id`를 가진다. 회전할 때 같은 값을 유지하고, 새 기기 로그인에서만 새 값을 만든다 (R4). | M |

### F1-02 맛집 관리

| ID | 요구사항 | 우선순위 |
|----|----------|----------|
| FR-02-01 | 로그인한 회원은 맛집을 등록할 수 있다. | M |
| FR-02-02 | 맛집은 이름, 카테고리, 주소, 설명을 가진다. 전화번호와 좌표는 선택 항목이다. | M |
| FR-02-03 | 맛집 수정·삭제는 **작성자 본인만** 할 수 있다. 다른 회원이 등록한 맛집은 수정·삭제할 수 없다. 관리자의 전체 맛집 관리는 F1-09에서 별도 API로 제공한다. | M |
| FR-02-04 | 맛집 목록은 페이지 단위로 조회한다. | M |
| FR-02-05 | 맛집은 카테고리 하나에 속한다. 카테고리 목록은 DB에서 관리한다. | M |
| FR-02-06 | 카테고리별로 맛집 목록을 필터링할 수 있다. | M |
| FR-02-07 | 맛집 이름과 주소에 대해 키워드 검색을 할 수 있다. | M |
| FR-02-08 | 맛집 상세 페이지에서 정보, 이미지, 평균 평점, 리뷰 목록을 볼 수 있다. | M |
| FR-02-09 | 맛집 삭제는 **관련 데이터를 포함한 완전 삭제**다. 리뷰, 찜, 이미지 메타데이터, AI 리뷰 요약을 함께 삭제하고, S3의 실제 이미지 파일도 삭제한다. 소프트 삭제는 사용하지 않는다. 처리 방식은 FR-03-06, FR-03-07과 NFR-17을 따른다. | M |

### F1-03 맛집 이미지

| ID | 요구사항 | 우선순위 |
|----|----------|----------|
| FR-03-01 | 맛집 작성자는 이미지를 업로드할 수 있다. | M |
| FR-03-02 | 이미지는 AWS S3에 저장하고 DB에는 객체 키와 메타데이터만 저장한다. | M |
| FR-03-03 | 허용 형식은 JPEG, PNG, WEBP이며, 파일당 최대 5MB, 맛집당 최대 5장으로 제한한다. | M |
| FR-03-04 | 이미지 삭제 또는 맛집 삭제 시 DB 메타데이터를 삭제하고, S3 객체도 삭제한다. 삭제 순서는 FUNCTION_SPEC F1-03을 따른다. | M |
| FR-03-05 | 이미지가 없는 맛집은 기본 이미지를 표시한다. | M |
| FR-03-06 | S3 객체 삭제가 실패하면 실패한 객체 키를 `storage_delete_task`에 기록하고, 관리자가 재시도할 수 있어야 한다 (재시도 API는 F1-09). | M |
| FR-03-07 | DB 삭제와 S3 삭제는 하나의 트랜잭션으로 묶이지 않는다. 따라서 두 저장소의 원자성을 보장한다고 표현하지 않으며, 실패는 FR-03-06의 추적·재시도로 보완한다. | M |

### F1-04 리뷰

| ID | 요구사항 | 우선순위 |
|----|----------|----------|
| FR-04-01 | 로그인한 회원은 맛집에 리뷰(내용 + 평점 1~5)를 작성할 수 있다. | M |
| FR-04-02 | 한 회원은 같은 맛집에 리뷰를 한 개만 작성할 수 있다. | M |
| FR-04-03 | 리뷰 삭제는 **리뷰 작성자 본인만** 할 수 있다. 관리자의 리뷰 관리는 F1-09에서 별도 API로 제공한다. | M |
| FR-04-04 | 맛집의 평균 평점과 리뷰 수를 계산해 표시한다. | M |
| FR-04-05 | 리뷰 작성·삭제 시 맛집의 평균 평점이 즉시 갱신된다. | M |

### F1-05 AI 리뷰 요약

| ID | 요구사항 | 우선순위 |
|----|----------|----------|
| FR-05-01 | 리뷰가 3개 이상인 맛집에 대해서만 AI 요약을 제공한다. | M |

## 3. 제약 사항

- 기술 스택은 [PROJECT_OVERVIEW.md](PROJECT_OVERVIEW.md#5-기술-스택-고정)에 정의된 목록으로 고정합니다.
- 맛집 데이터는 사용자 등록으로만 생성합니다. 외부 데이터 자동 수집은 하지 않습니다.
- AI 기능은 OpenRouter 한 곳만 사용합니다.
- 인증 수단: 화면은 Spring Security 세션, API는 JWT로 인증합니다 (2026-11-10 확정, FR-01-17~20). Google 로그인은 화면 로그인 흐름이며 OAuth2 임시 세션을 사용합니다.
- 운영 DB는 EC2 내부 MySQL 8입니다 (Q4). RDS는 이번 범위에서 사용하지 않습니다.
- DB 마이그레이션 도구(Flyway 등)는 이번 문서 범위에서 도입하지 않습니다. 도입은 설계 변경 절차를 거칩니다.
- 새로운 라이브러리나 프레임워크는 설계 변경 절차 없이 추가하지 않습니다.
